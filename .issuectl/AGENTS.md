# Agents policy (`.issuectl/AGENTS.md`)

What an agent needs to know about this repository's issue tracker beyond what
the `issuectl` binary and the `/issue` skill already say. The block between the
`issuectl-managed` sentinels at the bottom is the field reference;
`issuectl doctor --fix` regenerates it from the effective schema
(`issues/.schema.yaml` over issuectl's built-in fields), and the prose around
it is ours to keep true.

## The CLI owns `item.md`

Every issue is `issues/<slug>/item.md`, open or closed alike; the `status`
field decides, and nothing moves between directories. `issuectl` is the only
sane writer of that file: it validates against the schema, holds the write
lock in `.issuectl/write.lock`, stamps `updated`, and returns the version token
the next write passes back as `--expected-version`. A hand edit of frontmatter
skips all of that, and a hand-moved or hand-renamed directory leaves a slug
the CLI cannot find. Opening `item.md` in an editor is fine for reading and for
body prose the CLI has no section-level verb for (an issue's description);
frontmatter and directory layout stay with the CLI.

The verbs, the `--json` envelope and the query syntax are documented by the
binary itself (`issuectl <command> --help`) and by the installed `/issue`
skill. The skill is a copy frozen at the version it was installed for, and it
records that version; when it and the binary disagree, the binary is right and
`issuectl skill install issue --force` refreshes the copy. No transition rules
are declared in this repository, so the CLI will not stop a status jump that
makes no sense; that judgment is the agent's.

## What lives beside `item.md`

The other files under `issues/<slug>/` are the repository's own convention,
not the CLI's: `plan.md`, `analysis.md`, `design.md`, review reports and
assessments live there and nowhere else. They are the durable record of a
slice, because the worktree that produced them is gone after merge. A slice is
reviewed after it lands, so its review and the assessment of that review
belong beside the issue.

Reasons belong on the issue too. `issuectl note` appends timestamped blocks
(comments, `--decision`, `--agent-run`), and `issuectl close --comment` writes
the closing rationale under `## Resolution` in the same write as the status
change. A closed issue with a Resolution tells the next agent why; a bare
status flip does not, and that context is the thing a close can lose. Closing
itself is cheap to reverse: reopening appends a `## Reopen Notes` section
automatically. Which findings close as `wontfix`, which go to the
`multi-user-considerations` register instead of being fixed, and why, is
decided in the root `AGENTS.md`; the issue's own admission of low impact is the
close comment.

Issue text is public. Reproductions and evidence use synthetic companies and
amounts, never a real company's figures, counterparties or account data, and
never paths from someone's home directory.

Regulatory claims (Finnish accounting law, VAT, the VAT return's fields,
Tulorekisteri) in an issue, plan or review cite a primary source, such as the
law text or the authority's record specification. A model's recollection is
not a source.

Commits carry `Refs-Issue: @<slug>` or `Fixes-Issue: @<slug>` as a trailer;
`issuectl sync-commits` copies them onto the issue's `commits` list, and its
help text explains the range you need when running it on `main`.

## Scheduling state

`lane`, `lane_seq`, `collision` and `blocked_by` are the scheduler's state.
`issuectl dag` derives lanes, order and spawnable heads from them on every
read, and nothing else stores that structure, so it is merge-updated and never
regenerated from scratch. Every open issue is either in a lane or awaiting
triage; there is no backlog. The lane philosophy (serial queues at conflict
boundaries, collision tokens for shared files, the never-picked `parkki` lane
that `dag` still reports as spawnable) is in the root `AGENTS.md`.
